# ТЗ — починить GUI/VLM (vlm_task), vision worker и связанные баги Omnibot

Дата: 25.08.2026. Заказчик: пользователь. Исполнитель: разработчики Omnibot / плагина OmniFlow.

## 1. Цель
Починить автоматическое управление телефоном через GUI-плагин (vlm_task): сейчас плагин НЕ выполняет ни одного действия на экране, но возвращает «успех». Это блокирует любые задачи управления Android-приложениями (Facebook, Instagram и т.д.).

## 2. Окружение
- Приложение: Omnibot (debug-сборка, GUI/VLM плагин встроен)
- OmniFlow: плагин v2.1.7, runtime `2026.08.15.release.007fe8c7.a112f0d4.118fbd5b.0b2cb8a1`
- Устройство: Samsung, Android 15; ADB-бэкенд исправен
- Модель vision: deepseek-v4-flash-vision-exp (поле available_models в RunLog)

## 3. Симптом 1 (главный) — vlm_task возвращает success при 0 выполненных шагах
Три запуска 25.08.2026 (~19:03–19:05 Asia/Almaty) с разными целями (от простой «Открой приложение Facebook» до детальной):

| RunLog ID | status | step_count | action_count | token_usage |
|---|---|---|---|---|
| gui-33b591c1-35e5-4da2-88b5-3d05c9a0229f | succeeded | 0 | 0 | call_count=1, successful=0, **failed=1** |
| gui-1bc1f849-ecd1-4cd2-9418-b2506b5a29a2 | succeeded | 0 | 0 | failed_call_count=1 |
| gui-6e7a7c56-67ea-4b90-872b-2a21c5b8bfc3 | succeeded | 0 | 0 | call_count=1, successful=0, **failed=1** |

Факты:
- В `diagnostics.token_usage` у каждого запуска единственный вызов планировщика УПАЛ (failed_call_count=1, successful_call_count=0), но итоговый статус — `succeeded`, `success=true`, `done_reason=manual_finished`.
- Телефон при этом остаётся в приложении Omnibot: `final_state.package_name = cn.com.omnimind.bot` (см. state_7b483d92dcf8669e6d14, state_56d2c99adcf1b201c7a7). Ни одного GUI-действия не выполнено.
- `reload_omniflow_python_override` (перезапуск воркера) проблему НЕ решает.

Ожидание: при failed_call_count>0 и step_count=0 RunLog должен быть `failed` с текстом ошибки, а не `succeeded`.

## 4. Симптом 2 — неверное имя модели у планировщика (вероятная первопричина)
RunLog gui-a9bc195d-66c7-41df-b2fe-896f76f1df56 (24.08.2026), status=failed, ошибка:

```
vlm_planner_failed: chat completion stream request failed(400):
The supported API model names are deepseek-v4-pro, deepseek-v4-flash,
and deepseek-v4-flash-vision-exp, but you passed qwen3-vl-plus.
```

Выводы для исполнителя:
1. Где-то в конфиге GUI/VLM остался старый дефолт `qwen3-vl-plus`, который API (400) отвергает.
2. Скорее всего, поэтому и сегодня каждый вызов планировщика падает с 400, а ошибка ГЛОТАЕТСЯ — наружу уходит success + 0 шагов.
3. Нужно: (а) заменить qwen3-vl-plus на deepseek-v4-flash-vision-exp во всех конфигах/дефолтах; (б) не глотать ошибку планировщика — пробрасывать её в статус RunLog и в ответ vlm_task.

## 5. Симптом 3 — package_control.launch_activity отвечает invalid_arguments
Запросы:
- `{"package": "com.facebook.katana"}`
- `{"package": "com.facebook.katana", "activity": "com.facebook.katana.LoginActivity"}`

Оба возвращают `code=invalid_arguments`, message="The privileged action arguments are invalid." Схема аргументов нигде не описана. Нужно: опубликовать корректную схему аргументов или починить разбор параметров.

## 6. Симптом 4 — browser_use скриншоты (ретро, проверить)
24.08.2026 падало `browser_use` действие `screenshot` с `read_image=true` (точный текст ошибки в памяти за 24.08, файл `.omnibot/memory/short-memories/26-08-24.md`). Сейчас обходимся текстовым режимом. Просьба проверить путь скриншотов браузера.

## 7. Симптом 5 — эксклюзивность инструментов (платформенное ограничение)
`terminal_execute` и `android_privileged_action` эксклюзивны: при параллельном вызове с другими инструментами в одном ходе остальные падают с «Exclusive tool occupied this turn». Обходимся последовательными вызовами, но желательно убрать ограничение.

## 8. Шаги воспроизведения (для разработчика)
1. Вызвать vlm_task с простой целью, например «Открой приложение Facebook на телефоне».
2. Через ~1 сек приходит success=true, step_count=0, телефон остаётся в Omnibot.
3. Открыть RunLog (list_run_logs → get_run_log): в diagnostics видно failed_call_count=1 при статусе succeeded.

## 9. Критерии приёмки
1. vlm_task реально выполняет GUI-шаги на устройстве (скриншот → действие → скриншот), step_count>0 для задач с действиями.
2. При падении планировщика статус RunLog = failed + текст ошибки (никаких success + 0 steps).
3. Дефолтная модель GUI/VLM = deepseek-v4-flash-vision-exp; qwen3-vl-plus нигде не передаётся.
4. Документирована/починена схема аргументов package_control.launch_activity.
5. (Опционально) browser_use screenshot read_image=true работает без падений.
